**Observed in source, 19 November 2026.** In `@medusajs/dashboard@2.22.7/dist`, both `product-create-*.mjs` and `product-media-*.mjs` call `sdk.admin.upload.create` before attaching the returned URLs. The edit dialog submits `images` and `thumbnail` separately to the product mutation. In `@medusajs/medusa/dist/api/admin/uploads/route.js`, the handler passes file buffers to `uploadFilesWorkflow` with public access. The upload alone carries no product ID. The storefront uses unoptimized images. Its configured hosts include upstream S3 assets. [App image config](../../../apps/storefront/next.config.js) · [Seed catalog](../../../apps/backend/src/migration-scripts/initial-data-seed.ts)

**Decision for I1.** Add a merchant action on an existing product. Create the product first when adding new media. The authenticated action records product ID, upload ID and expected media version, then streams one bounded original into private storage. Keep the existing public catalog URL until the worker commits a successful result. A generic replacement of the upload provider would still attach a URL before processing finishes. Demonstrate the new action explicitly and preserve the existing seeded catalog.

**Proposed I2–I4 contract.** Accept JPEG and PNG initially. Start with a 5 MiB upload cap and a 16-megapixel decoded cap. Produce bounded 320 px and 1024 px derivatives without upscaling. Use the source generation in every derivative and result key. The function writes a success result only after both objects exist. The worker checks the current upload ID under a product-scoped lock before attachment. Verify dimensions, MIME, stale-result handling and a worker restart between reading the result and updating the product. The merchant sees a failed state for rejected inputs. Size limits require a memory/time pilot within P3. Use the same project and `us-central1` for the originals bucket, storage trigger and function.
